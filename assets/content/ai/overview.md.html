生成式 AI (GenAI) 結合大型語言模型 (LLMs) 可用於建立複雜且引人入勝的應用體驗，包括個性化內容、智慧推薦、媒體生成和理解、訊息摘要以及動態功能。

開發此類別功能以前需要深厚的領域專業知識和大量的工程投入。然而，新產品和 SDK 正在降低入門門檻。Angular 非常適合將 AI 整合到您的 Web 應用中，原因如下：

  • Angular 強大的範本 API 支援建立由生成內容組成的動態、簡潔的 UI
  • 強大的、基於訊號的架構，旨在動態管理資料和狀態
  • Angular 與 AI SDK 和 API 無縫整合

本指南示範了如何使用 Genkit、Firebase AI Logic 和 Gemini API 為您的 Angular 應用注入 AI。本指南將透過解釋如何開始將 AI 整合到 Angular 應用中，來啟動您的 AI 驅動的 Web 應用開發之旅。本指南還分享了入門資源，例如入門套件、範例程式碼和常見工作流的配方，您可以快速上手。

開始之前，您應該對 Angular 有基本的瞭解。剛接觸 Angular？請嘗試我們的基礎指南或我們的入門教學課程。

注意：雖然此頁面展示了與 Google AI 產品的整合和範例，但像 Genkit 這樣的工具是模型無關的，允許您選擇自己的模型。在許多情況下，範例和程式碼樣本適用於其他第三方解決方案。

入門

建立 AI 驅動的應用是一個新興且快速發展的領域。決定從哪裡開始以及選擇哪些技術可能具有挑戰性。以下部分提供了三種選擇：

  1. Genkit 為您提供了用於建立全棧應用的支援的模型和統一 API 介面。非常適合需要複雜後端 AI 邏輯的應用，例如個性化推薦。

  2. Firebase AI Logic 為 Google 的模型提供安全的用戶端 API，用於建立僅用戶端應用或移動應用。最適合瀏覽器中的互動式 AI 功能，例如實時文字分析或基本聊天機器人。

  3. Gemini API 使您能夠直接建立使用透過 API 表面公開的方法和功能的應用程式，最適合全棧應用。適用於需要直接控制 AI 模型（如自定義影象生成或深度資料處理）的應用。

最佳實踐

連線模型提供商並確保 API 憑證安全

連線模型提供商時，務必妥善保管您的 API 金鑰。切勿將 API 金鑰放入傳送到用戶端的檔案中，例如 environments.ts。

您的應用架構決定了選擇哪些 AI API 和工具。具體來說，根據您的應用是用戶端還是伺服器端來選擇。像 Firebase AI Logic 這樣的工具為用戶端程式碼提供了與模型 API 的安全連線。如果您想使用 Firebase AI Logic 以外的其他 API，或者更喜歡使用其他模型提供商，請考慮建立一個代理伺服器，甚至使用 Cloud Functions for Firebase 作為代理，以避免暴露您的 API 金鑰。

有關使用用戶端應用進行連線的範例，請參閱程式碼：Firebase AI Logic Angular 範例儲存庫。

對於需要 API 金鑰的伺服器端連線到模型 API，請優先使用金鑰管理器或環境變數，而不是 environments.ts。您應該遵循保護 API 金鑰和憑證的標準最佳實踐。Firebase 現在透過 Firebase App Hosting 的最新更新提供了一個新的金鑰管理器。要了解更多訊息，請檢視官方文件。

有關全棧應用中的伺服器端連線範例，請參閱程式碼：Angular AI 範例（Genkit 和 Angular 故事產生器）儲存庫。

使用工具呼叫增強應用

如果您想建立 Agentic 工作流，即代理能夠根據提示採取行動並使用工具來解決問題，請使用『工具呼叫』。工具呼叫，也稱為函式呼叫，是一種讓 LLM 能夠向呼叫它的應用程式發出請求的方式。作為開發人員，您可以定義哪些工具可用，並控制如何或何時呼叫這些工具。

工具呼叫透過將您的 AI 整合擴充套件到問答式聊天機器人之外，進一步增強了您的 Web 應用。事實上，您可以透過模型提供商的函式呼叫 API，讓您的模型能夠請求函式呼叫。可用的工具可用於在您的應用程式上下文中執行更復雜的操作。

在 Angular 範例儲存庫的電子商務範例中，LLM 請求呼叫函式庫存函式以獲得執行更復雜任務所需的上下文，例如計算商店中一組商品的價格。可用的 API 範圍由您作為開發人員決定，就像是否呼叫 LLM 請求的函式一樣。您仍然可以控制執行流程。例如，您可以公開服務中的特定函式，但不是該服務的所有函式。

處理非確定性回應

由於模型可能回傳非確定性結果，因此您的應用程式應考慮到這一點。以下是您可以在應用程式實現中使用的一些策略：

  • 調整提示和模型引數（例如溫度）以獲得更多或更少的確定性回應。您可以在 ai.google.dev 的提示策略部分找到更多訊息。
  • 使用『人工干預』策略，即由人工在工作流中進行下一步操作之前驗證輸出。建立您的應用程式工作流，允許操作員（人類別或其他模型）驗證輸出並確認關鍵決策。
  • 利用工具（或函式）呼叫和模式約束來指導和限制模型回應以符合預定義格式，從而提高回應的可預測性。

即使考慮了這些策略和技術，也應在應用程式設計中加入合理的備用方案。遵循現有的應用程式彈性標準。例如，如果資源或 API 不可用，應用程式崩潰是不可接受的。在這種情況下，會向用戶顯示錯誤訊息，並在適用時顯示後續步驟的選項。建立 AI 驅動的應用程式需要同樣的考慮。確認回應與預期輸出一致，並在不一致時透過優雅降級提供『安全著陸』。這也適用於 LLM 提供商的 API 故障。

考慮以下範例：LLM 提供商沒有回應。處理中斷的一種潛在策略是：

  • 儲存使用者的回應，以便在重試場景中使用（現在或稍後）
  • 向用戶發出中斷警報，並附帶一條不洩露敏感訊息的適當訊息
  • 在服務恢復可用後，稍後恢復對話。
