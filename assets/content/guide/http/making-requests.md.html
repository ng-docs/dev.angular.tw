發出 HTTP 請求

edit

HttpClient 提供了對應不同 HTTP 動詞的方法，用於發起請求以載入資料或在服務器上應用更改。每個方法都會回傳一個 RxJS Observable，訂閱該 Observable 後會傳送請求，並在伺服器回應時發出結果。

注意： 由 HttpClient 建立的 Observable 可以被訂閱任意次數，並且每次訂閱都會發起一個新的後端請求。

透過傳遞給請求方法的選項物件，可以調整請求的各種屬性以及回傳的回應型別。

獲取 JSON 資料

從後端獲取資料通常需要使用 HttpClient.get() 方法發起 GET 請求。此方法接受兩個引數：要從中獲取資料的字串端點 URL，以及一個用於設定請求的可選選項物件。

例如，使用 HttpClient.get() 方法從假設的 API 獲取設定資料：

http.get<Config>('/api/config').subscribe(config => {  // process the configuration.});

請注意泛型型別引數，它指定伺服器回傳的資料將為 Config 型別。此引數是可選的，如果省略它，則回傳的資料將具有 Object 型別。

提示： 當處理結構不確定的資料以及潛在的 undefined 或 null 值時，請考慮使用 unknown 型別而不是 Object 作為回應型別。

重要：請求方法的泛型型別是對伺服器回傳資料的型別斷言。HttpClient 不會驗證實際回傳資料是否與此類型對應。

獲取其他型別的資料

預設情況下，HttpClient 假定伺服器回傳 JSON 資料。在與非 JSON API 互動時，您可以告知 HttpClient 在發起請求時期望和回傳的回應型別。這可以透過 responseType 選項來完成。

responseType 值 回傳的回應型別
'json' (預設值) 給定泛型型別的 JSON 資料
'text' 字串資料
'arraybuffer' ArrayBuffer，其中包含原始回應位元組
'blob' Blob 實例

例如，您可以要求 HttpClient 將 .jpeg 影象的原始位元組下載到 ArrayBuffer 中：

http.get('/images/dog.jpg', {responseType: 'arraybuffer'}).subscribe(buffer => {  console.log('The image is ' + buffer.byteLength + ' bytes large');});

responseType 的字面量值

由於 responseType 的值會影響 HttpClient 回傳的型別，因此它必須是字面量型別，而不是 string 型別。

如果傳遞給請求方法的選項物件是字面量物件，則會自動發生這種情況，但是如果您要將請求選項提取到變數或輔助函式中，則可能需要將其顯式指定為字面量，例如 responseType: 'text' as const。

變更伺服器狀態

執行變更的伺服器 API 通常需要發出 POST 請求，並在請求正文中指定新狀態或要進行的更改。

HttpClient.post() 方法的行為與 get() 類似，並在其選項之前接受一個額外的 body 引數：

http.post<Config>('/api/config', newConfig).subscribe(config => {  console.log('Updated config:', config);});

可以為請求的 body 提供許多不同型別的值，HttpClient 會相應地對其進行序列化：

body 型別 序列化為
string 純文字
數字、布林值、陣列或普通物件 JSON
ArrayBuffer 來自緩衝區的原始資料
Blob 具有 Blob 內容型別的原始資料
FormData multipart/form-data 編碼的資料
HttpParams 或 URLSearchParams application/x-www-form-urlencoded 格式化字串

重要提示： 請記住 .subscribe() 變更請求 Observable，以便實際觸發請求。

設定 URL 引數

使用 params 選項指定應包含在請求 URL 中的請求引數。

傳遞物件字面量是設定 URL 引數的最簡單方法：

http.get('/api/config', {  params: {filter: 'all'},}).subscribe(config => {  // ...});

或者，如果你需要對引數的構造或序列化進行更多控制，可以傳遞一個 HttpParams 實例。

重要提示：HttpParams 的實例是不可變的，不能直接更改。相反，像 append() 這樣的變更方法會回傳一個應用了變更的新 HttpParams 實例。

const baseParams = new HttpParams().set('filter', 'all');http.get('/api/config', {  params: baseParams.set('details', 'enabled'),}).subscribe(config => {  // ...});

你可以使用自定義的 HttpParameterCodec 來實例化 HttpParams，該編解碼器決定了 HttpClient 將如何將引數編碼到 URL 中。

設定請求標頭

使用 headers 選項指定應包含在請求中的請求標頭。

傳遞物件字面量是設定請求標頭最簡單的方法：

http.get('/api/config', {  headers: {    'X-Debug-Level': 'verbose',  }}).subscribe(config => {  // ...});

或者，如果你需要對標頭構造進行更多控制，可以傳遞一個 HttpHeaders 實例。

重要提示：HttpHeaders 的實例是不可變的，不能直接更改。相反，像 append() 這樣的變更方法會回傳一個應用了變更的新 HttpHeaders 實例。

const baseHeaders = new HttpHeaders().set('X-Debug-Level', 'minimal');http.get<Config>('/api/config', {  headers: baseHeaders.set('X-Debug-Level', 'verbose'),}).subscribe(config => {  // ...});

與伺服器回應事件互動

為了方便起見，HttpClient 預設回傳一個伺服器回傳的資料（回應體）的Observable。有時檢查實際回應是可取的，例如檢索特定的回應標頭。

要訪問完整的回應，請將 observe 選項設定為 'response'：

http.get<Config>('/api/config', {observe: 'response'}).subscribe(res => {  console.log('Response status:', res.status);  console.log('Body:', res.body);});

observe 的字面量值

因為 observe 的值會影響 HttpClient 回傳的型別，所以它必須具有字面量型別而不是 string 型別。

如果傳遞給請求方法的選項物件是字面量物件，則會自動發生這種情況；但是，如果要將請求選項提取到變數或輔助方法中，則可能需要顯式地將其指定為字面量，例如 observe: 'response' as const。

接收原始進度事件

除了回應體或回應物件之外，HttpClient 還可以回傳一個原始事件流，對應於請求生命週期中的特定時刻。這些事件包括請求傳送時、回應標頭回傳時以及正文完成時。這些事件還可以包括進度事件，報告大型請求或回應體的上傳和下載狀態。

預設情況下，進度事件處於停用狀態（因為它們會產生效能成本），但可以使用 reportProgress 選項啟用。

注意：HttpClient 的可選 fetch 實現不報告上傳進度事件。

要觀察事件流，請將 observe 選項設定為 'events'：

http.post('/api/upload', myData, {  reportProgress: true,  observe: 'events',}).subscribe(event => {  switch (event.type) {    case HttpEventType.UploadProgress:      console.log('Uploaded ' + event.loaded + ' out of ' + event.total + ' bytes');      break;    case HttpEventType.Response:      console.log('Finished uploading!');      break;  }});

observe 的字面量值

因為 observe 的值會影響 HttpClient 回傳的型別，所以它必須具有字面量型別而不是 string 型別。

如果傳遞給請求方法的選項物件是字面量物件，則會自動發生這種情況；但是，如果要將請求選項提取到變數或輔助方法中，則可能需要顯式地將其指定為字面量，例如 observe: 'events' as const。

事件流中報告的每個 HttpEvent 都有一個 type，用於區分事件代表的內容：

type 值 事件含義
HttpEventType.Sent 請求已排程到伺服器
HttpEventType.UploadProgress 一個 HttpUploadProgressEvent，報告上傳請求正文的進度
HttpEventType.ResponseHeader 已接收到回應頭，包括狀態和標頭
HttpEventType.DownloadProgress 一個 HttpDownloadProgressEvent，報告下載回應正文的進度
HttpEventType.Response 已接收到整個回應，包括回應主體
HttpEventType.User 來自 Http 攔截機制的自定義事件。

處理請求失敗

HTTP 請求可能失敗的三種方式：

  • 網路或連線錯誤可能會阻止請求到達後端伺服器。
  • 設定了 timeout 選項時，請求未及時回應。
  • 後端可以接收請求，但無法處理它，並回傳錯誤回應。

HttpClient 會將上述所有型別的錯誤捕獲在 HttpErrorResponse 中，並透過 Observable 的錯誤通道回傳。網路和超時錯誤的狀態碼為 0，error 是 ProgressEvent 的實例。後端錯誤則具有後端回傳的失敗狀態碼，以及作為 error 的錯誤回應。檢查回應以確定錯誤的根本原因和處理錯誤的適當操作。

RxJS 函式庫提供了幾個運算子，這些運算子對於錯誤處理非常有用。

你可以使用 catchError 運算子將錯誤回應轉換為 UI 的值。此值可以告知 UI 顯示錯誤頁面或值，並在必要時捕獲錯誤的原因。

有時，諸如網路中斷之類別的瞬時錯誤可能會導致請求意外失敗，而只需重試請求即可使其成功。RxJS 提供了幾個 retry 運算子，這些運算子在特定條件下會自動重新訂閱失敗的 Observable。例如，retry() 運算子將自動嘗試重新訂閱指定的次數。

超時

要為請求設定超時，可以在其他請求選項中將 timeout 選項設定為毫秒數。如果在指定時間內後端請求未完成，則請求將被中止併發出錯誤。

注意：超時僅適用於後端 HTTP 請求本身。它不是整個請求處理鏈的超時。因此，此選項不受攔截器引入的任何延遲影響。

http.get('/api/config', {  timeout: 3000,}).subscribe({  next: config => {    console.log('Config fetched successfully:', config);  },  error: err => {    // If the request times out, an error will have been emitted.  }});

高階 fetch 選項

在使用 withFetch() 提供者時，Angular 的 HttpClient 提供了對高階 fetch API 選項的訪問，這些選項可以提高效能和使用者體驗。這些選項僅在使用 fetch 後端時可用。

Fetch 選項

以下選項在使用 fetch 後端時提供對請求行為的細粒度控制。

保持連線

keepalive 選項允許請求的生存期超過發起它的頁面。這對於需要即使在使用者離開頁面後也能完成的分析或日誌記錄請求特別有用。

http.post('/api/analytics', analyticsData, {  keepalive: true}).subscribe();

HTTP 快取控制

cache 選項控制請求如何與瀏覽器的 HTTP 快取進行互動，這可以顯著提高重複請求的效能。

//  Use cached response regardless of freshnesshttp.get('/api/config', {  cache: 'force-cache'}).subscribe(config => {  // ...});// Always fetch from network, bypass cachehttp.get('/api/live-data', {  cache: 'no-cache'}).subscribe(data => {  // ...});// Use cached response only, fail if not in cachehttp.get('/api/static-data', {  cache: 'only-if-cached'}).subscribe(data => {  // ...});

Core Web Vitals 的請求優先級

priority 選項允許你指示請求的相對重要性，幫助瀏覽器最佳化資源載入以獲得更好的 Core Web Vitals 分數。

// High priority for critical resourceshttp.get('/api/user-profile', {  priority: 'high'}).subscribe(profile => {  // ...});// Low priority for non-critical resourceshttp.get('/api/recommendations', {  priority: 'low'}).subscribe(recommendations => {  // ...});// Auto priority (default) lets the browser decidehttp.get('/api/settings', {  priority: 'auto'}).subscribe(settings => {  // ...});

可用的 priority 值：

  • 'high'：高優先級，提前載入（例如，關鍵使用者資料，首屏內容）
  • 'low'：低優先級，在資源可用時載入（例如，分析，預取資料）
  • 'auto'：瀏覽器根據請求上下文確定優先級（預設）

提示：對影響最大內容繪製 (LCP) 的請求使用 priority: 'high'，對不影響初始使用者體驗的請求使用 priority: 'low'。

請求模式

mode 選項控制請求如何處理跨域請求並確定回應型別。

// Same-origin requests onlyhttp.get('/api/local-data', {  mode: 'same-origin'}).subscribe(data => {  // ...});// CORS-enabled cross-origin requestshttp.get('https://api.external.com/data', {  mode: 'cors'}).subscribe(data => {  // ...});// No-CORS mode for simple cross-origin requestshttp.get('https://external-api.com/public-data', {  mode: 'no-cors'}).subscribe(data => {  // ...});

可用的 mode 值：

  • 'same-origin'：僅允許同源請求，跨域請求失敗
  • 'cors'：允許帶 CORS 的跨域請求（預設）
  • 'no-cors'：允許不帶 CORS 的簡單跨域請求，回應是匿名的

提示：對不應跨域的敏感請求使用 mode: 'same-origin'。

重導向處理

redirect 選項指定如何處理來自伺服器的重導向回應。

// Follow redirects automatically (default behavior)http.get('/api/resource', {  redirect: 'follow'}).subscribe(data => {  // ...});// Prevent automatic redirectshttp.get('/api/resource', {  redirect: 'manual'}).subscribe(response => {  // Handle redirect manually});// Treat redirects as errorshttp.get('/api/resource', {  redirect: 'error'}).subscribe({  next: data => {    // Success response  },  error: err => {    // Redirect responses will trigger this error handler  }});

可用的 redirect 值：

  • 'follow'：自動跟隨重導向（預設）
  • 'error'：將重導向視為錯誤
  • 'manual'：不自動跟蹤重導向，回傳重導向回應

提示：當您需要使用自定義邏輯處理重導向時，請使用 redirect: 'manual'。

憑證處理

credentials 選項控制是否將 cookie、授權標頭和其他憑證與跨域請求一起傳送。這對於身份驗證場景尤其重要。

// Include credentials for cross-origin requestshttp.get('https://api.example.com/protected-data', {  credentials: 'include'}).subscribe(data => {  // ...});// Never send credentials (default for cross-origin)http.get('https://api.example.com/public-data', {  credentials: 'omit'}).subscribe(data => {  // ...});// Send credentials only for same-origin requestshttp.get('/api/user-data', {  credentials: 'same-origin'}).subscribe(data => {  // ...});// withCredentials overrides credentials settinghttp.get('https://api.example.com/data', {  credentials: 'omit',        // This will be ignored  withCredentials: true       // This forces credentials: 'include'}).subscribe(data => {  // Request will include credentials despite credentials: 'omit'});// Legacy approach (still supported)http.get('https://api.example.com/data', {  withCredentials: true}).subscribe(data => {  // Equivalent to credentials: 'include'});

重要提示：withCredentials 選項優先於 credentials 選項。如果同時指定了兩者，則 withCredentials: true 始終會導致 credentials: 'include'，而忽略顯式的 credentials 值。

可用的 credentials 值：

  • 'omit'：從不傳送憑證
  • 'same-origin'：僅為同源請求傳送憑證（預設）
  • 'include'：始終傳送憑證，即使是跨域請求

提示：當您需要將身份驗證 cookie 或標頭傳送到支援 CORS 的不同域時，請使用 credentials: 'include'。為避免混淆，請避免混合使用 credentials 和 withCredentials 選項。

引用者

referrer 選項允許您控制隨請求傳送的引用者訊息。這對於隱私和安全考慮很重要。

// Send a specific referrer URLhttp.get('/api/data', {  referrer: 'https://example.com/page'}).subscribe(data => {  // ...});// Use the current page as referrer (default behavior)http.get('/api/analytics', {  referrer: 'about:client'}).subscribe(data => {  // ...});

referrer 選項接受：

  • 有效的 URL 字串：設定要傳送的特定引用者 URL
  • 空字串 ''：不傳送引用者訊息
  • 'about:client'：使用預設引用者（當前頁面 URL）

提示：對於敏感請求，如果您不想洩露引用頁面的 URL，請使用 referrer: ''。

完整性

integrity 選項允許您透過提供預期內容的加密雜湊來驗證回應未被篡改。這對於從 CDN 載入指令碼或其他資源特別有用。

// Verify response integrity with SHA-256 hashhttp.get('/api/script.js', {  integrity: 'sha256-ABC123...',  responseType: 'text'}).subscribe(script => {  // Script content is verified against the hash});

重要提示：integrity 選項要求回應內容與提供的雜湊值完全對應。如果內容不對應，請求將因網路錯誤而失敗。

提示：從外部源載入關鍵資源時，請使用子資源完整性來確保它們未被修改。使用 openssl 等工具生成雜湊值。

Http Observable

HttpClient 上的每個請求方法都會構造並回傳所請求回應型別的 Observable。在使用 HttpClient 時，理解這些 Observable 的工作方式很重要。

HttpClient 生成的是 RxJS 所稱的『冷』Observable，這意味著在訂閱 Observable 之前不會發生實際的請求。只有那時，請求才會被實際分派到伺服器。多次訂閱同一個 Observable 會觸發多個後端請求。每次訂閱都是獨立的。

提示：您可以將 HttpClient Observables 視為實際伺服器請求的藍圖。

一旦訂閱，取消訂閱將中止正在進行的請求。如果 Observable 是透過 async 通道訂閱的，這將非常有用，因為它會在使用者離開當前頁面時自動取消請求。此外，如果將 Observable 與 RxJS 組合器（如 switchMap）一起使用，則此取消將清除任何過時的請求。

回應回傳後，來自 HttpClient 的 Observable 通常會完成（儘管攔截器可能會影響這一點）。

由於自動完成，如果 HttpClient 訂閱未被清理，通常沒有記憶體洩漏的風險。但是，與任何非同步操作一樣，我們強烈建議在銷燬使用它們的元件時清理訂閱，因為否則訂閱回呼可能會在嘗試與已銷燬的元件互動時運行並遇到錯誤。

提示：使用 async 通道或 toSignal 操作來訂閱 Observables 可確保正確處理訂閱。

最佳實踐

雖然 HttpClient 可以直接從元件注入和使用，但通常我們建議您建立可重用的、可注入的服務，這些服務可以隔離和封裝資料訪問邏輯。例如，此 UserService 封裝了根據使用者 ID 請求使用者資料的邏輯：

@Injectable({providedIn: 'root'})export class UserService {  private http = inject(HttpClient);  getUser(id: string): Observable<User> {    return this.http.get<User>(`/api/user/${id}`);  }}

在元件中，你可以將 @if 與 async 通道結合使用，以便僅在資料載入完成後才渲染資料的 UI：

import { AsyncPipe } from '@angular/common';@Component({  imports: [AsyncPipe],  template: `    @if (user$ | async; as user) {      <p>Name: {{ user.name }}</p>      <p>Biography: {{ user.biography }}</p>    }  `,})export class UserProfileComponent {  userId = input.required<string>();  user$!: Observable<User>;  private userService = inject(UserService);  constructor(): void {    effect(() => {      this.user$ = this.userService.getUser(this.userId());    });  }}
