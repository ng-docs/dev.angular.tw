伺服器端渲染和混合渲染

edit

Angular 預設將所有應用作為用戶端渲染 (CSR) 應用發布。雖然這種方法提供的初始負載很輕，但它也帶來了權衡，包括載入時間變慢、效能指標下降以及更高的資源需求，因為使用者裝置執行了大部分計算。因此，許多應用透過將伺服器端渲染 (SSR) 整合到混合渲染策略中，實現了顯著的效能改進。

什麼是混合渲染？

混合渲染允許開發人員利用伺服器端渲染 (SSR)、預渲染（也稱為『靜態站點生成』或 SSG）和用戶端渲染 (CSR) 的優勢來最佳化您的 Angular 應用。它讓您可以精細地控制應用的不同部分的渲染方式，從而為使用者提供最佳體驗。

設定混合渲染

您可以使用 Angular CLI 的 ng new 指令配合伺服器端渲染標誌（即 --ssr）來建立一個支援混合渲染的新專案：

ng new --ssr

您也可以使用 ng add 指令將伺服器端渲染新增到現有專案中，以啟用混合渲染：

ng add @angular/ssr

注意：預設情況下，Angular 會預渲染您的整個應用程式並生成一個伺服器檔案。要停用此功能並建立完全靜態的應用，請將 outputMode 設定為 static。要啟用 SSR，請將伺服器路由更新為使用 RenderMode.Server。有關更多詳細訊息，請參閱 伺服器路由 和 生成完全靜態的應用。

伺服器路由

設定服務器路由

您可以透過宣告一個 ServerRoute 物件陣列來建立伺服器路由設定。此設定通常位於名為 app.routes.server.ts 的檔案中。

// app.routes.server.tsimport { RenderMode, ServerRoute } from '@angular/ssr';export const serverRoutes: ServerRoute[] = [  {    path: '', // This renders the "/" route on the client (CSR)    renderMode: RenderMode.Client,  },  {    path: 'about', // This page is static, so we prerender it (SSG)    renderMode: RenderMode.Prerender,  },  {    path: 'profile', // This page requires user-specific data, so we use SSR    renderMode: RenderMode.Server,  },  {    path: '**', // All other routes will be rendered on the server (SSR)    renderMode: RenderMode.Server,  },];

您可以使用 provideServerRendering 和 withRoutes 函式將此設定新增到您的應用程式中：

import { provideServerRendering, withRoutes } from '@angular/ssr';import { serverRoutes } from './app.routes.server';// app.config.server.tsconst serverConfig: ApplicationConfig = {  providers: [    provideServerRendering(withRoutes(serverRoutes)),    // ... other providers ...  ]};

在使用 應用外殼模式時，您必須為用戶端渲染的路由指定用作應用外殼的元件。為此，請使用 withAppShell 功能：

import { provideServerRendering, withRoutes, withAppShell } from '@angular/ssr';import { AppShellComponent } from './app-shell/app-shell.component';const serverConfig: ApplicationConfig = {  providers: [    provideServerRendering(      withRoutes(serverRoutes),      withAppShell(AppShellComponent),    ),    // ... other providers ...  ]};

渲染模式

伺服器路由設定允許您透過設定 RenderMode 來指定應用程式中每個路由的渲染方式：

渲染模式 描述
伺服器端 (SSR) 為每個請求在服務器上渲染應用程式，將一個完全填充的 HTML 頁面傳送到瀏覽器。
用戶端 (CSR) 在瀏覽器中渲染應用程式。這是 Angular 的預設行為。
預渲染 (SSG) 在建立時預渲染應用程式，為每個路由生成靜態 HTML 檔案。

選擇渲染模式

每種渲染模式都有不同的優點和缺點。您可以根據應用的具體需求選擇渲染模式。

用戶端渲染 (CSR)

用戶端渲染具有最簡單的開發模式，因為您可以編寫假定程式碼始終在 Web 瀏覽器中執行的程式碼。這使您可以使用廣泛的用戶端函式庫，這些函式庫也假定它們在瀏覽器中執行。

用戶端渲染的效能通常比其他渲染模式差，因為它必須在使用者看到任何渲染內容之前下載、解析和執行您頁面的 JavaScript。如果您的頁面在渲染時從伺服器獲取更多資料，使用者還必須等待這些額外的請求才能檢視完整內容。

如果您的頁面被搜尋引擎爬蟲索引，用戶端渲染可能會對搜尋引擎最佳化 (SEO) 產生負面影響，因為搜尋引擎爬蟲在索引頁面時對其執行的 JavaScript 量有限制。

在進行用戶端渲染時，伺服器除了提供靜態 JavaScript 資源外，無需執行任何渲染工作。如果伺服器成本是一個考慮因素，您可以考慮此因素。

支援透過 service workers 實現可安裝的離線體驗的應用，可以在無需與伺服器通訊的情況下依賴用戶端渲染。

伺服器端渲染 (SSR)

伺服器端渲染比用戶端渲染提供更快的頁面載入速度。伺服器在收到瀏覽器請求後，無需等待 JavaScript 下載和執行，而是直接渲染 HTML 文件。使用者只會體驗到伺服器獲取資料和渲染請求頁面所需的延遲。此模式還消除了瀏覽器進行額外網路請求的需要，因為您的程式碼可以在服務器渲染期間獲取資料。

伺服器端渲染通常具有出色的搜尋引擎最佳化 (SEO)，因為搜尋引擎爬蟲會收到一個完全渲染的 HTML 文件。

伺服器端渲染要求您編寫不嚴格依賴瀏覽器 API 的程式碼，並限制您選擇假定在瀏覽器中執行的 JavaScript 函式庫。

在進行伺服器端渲染時，您的伺服器會執行 Angular 為每個請求生成 HTML 回應，這可能會增加伺服器託管成本。

建立時預渲染

預渲染比用戶端渲染和伺服器端渲染都提供更快的頁面載入速度。由於預渲染在建立時建立 HTML 文件，伺服器可以直接以靜態 HTML 文件回應請求，無需任何額外工作。

預渲染要求在建立時即可獲得渲染頁面所需的所有訊息。這意味著預渲染的頁面不能包含特定於載入頁面的使用者的資料。預渲染主要適用於對應用的所有使用者都相同的頁面。

由於預渲染在建立時發生，它可能會為您的生產建立增加顯著的時間。使用 getPrerenderParams 生成大量 HTML 文件可能會影響您部署的總檔案大小，從而導致部署變慢。

預渲染通常具有出色的搜尋引擎最佳化 (SEO)，因為搜尋引擎爬蟲會收到一個完全渲染的 HTML 文件。

預渲染要求您編寫不嚴格依賴瀏覽器 API 的程式碼，並限制您選擇假定在瀏覽器中執行的 JavaScript 函式庫。

預渲染在每次伺服器請求時產生的開銷極小，因為您的伺服器會回應靜態 HTML 文件。靜態檔案還可以輕鬆地被內容分發網路 (CDN)、瀏覽器和中間快取層快取，以實現更快的後續頁面載入。完全靜態的網站還可以僅透過 CDN 或靜態檔案伺服器進行部署，從而無需為您的應用維護自定義伺服器執行時。這透過將工作從應用 Web 伺服器解除安裝來增強可擴充套件性，使其對高流量應用特別有利。

注意：使用 Angular service worker 時，第一個請求是伺服器端渲染的，但所有後續請求都由 service worker 處理並進行用戶端渲染。

設定標頭和狀態碼

您可以使用 ServerRoute 設定中的 headers 和 status 屬性為單個伺服器路由設定自定義標頭和狀態碼。

// app.routes.server.tsimport { RenderMode, ServerRoute } from '@angular/ssr';export const serverRoutes: ServerRoute[] = [  {    path: 'profile',    renderMode: RenderMode.Server,    headers: {      'X-My-Custom-Header': 'some-value',    },    status: 201,  },  // ... other routes];

重導向

Angular 在服務器端以不同的方式處理路由設定中由 redirectTo 屬性指定的重導向。

伺服器端渲染 (SSR) 重導向在服務器端渲染過程中使用標準的 HTTP 重導向（例如 301、302）執行。

預渲染 (SSG) 重導向透過預渲染的 HTML 中的 <meta http-equiv="refresh"> 標籤實現為『軟重導向』。

自定義建立時預渲染 (SSG)

使用 RenderMode.Prerender 時，您可以指定多個設定選項來定製預渲染和提供過程。

引數化路由

對於每個使用 RenderMode.Prerender 的路由，您可以指定一個 getPrerenderParams 函式。此函式允許您控制哪些特定引數會生成單獨的預渲染文件。

getPrerenderParams 函式回傳一個 Promise，該 Promise 解析為一個物件陣列。每個物件都是一個路由引數名到值的鍵值對映。例如，如果您定義了一個像 post/:id 這樣的路由，getPrerenderParams 可以回傳陣列 [{id: 123}, {id: 456}]，從而為 post/123 和 post/456 渲染單獨的文件。

getPrerenderParams 的主體可以使用 Angular 的 inject 函式來注入依賴項並執行任何工作以確定要預渲染的路由。這通常包括發出請求以獲取資料來建立引數值陣列。

您還可以將此函式與萬用字元路由（例如 /**）一起使用，其中引數名將是 "**"，回傳值將是路徑的片段，例如 foo/bar。這些可以與其他引數（例如 /post/:id/**）結合使用以處理更復雜的路由設定。

// app.routes.server.tsimport { RenderMode, ServerRoute } from '@angular/ssr';export const serverRoutes: ServerRoute[] = [  {    path: 'post/:id',    renderMode: RenderMode.Prerender,    async getPrerenderParams() {      const dataService = inject(PostService);      const ids = await dataService.getIds(); // Assuming this returns ['1', '2', '3']      return ids.map(id => ({ id })); // Generates paths like: /post/1, /post/2, /post/3    },  },  {    path: 'post/:id/**',    renderMode: RenderMode.Prerender,    async getPrerenderParams() {      return [        { id: '1', '**': 'foo/3' },        { id: '2', '**': 'bar/4' },      ]; // Generates paths like: /post/1/foo/3, /post/2/bar/4    },  },];

由於 getPrerenderParams 僅適用於 RenderMode.Prerender，因此此函式始終在建立時執行。getPrerenderParams 不能依賴任何特定於瀏覽器或特定於伺服器的 API 來獲取資料。

重要提示：在 getPrerenderParams 中使用 inject 時，請記住 inject 必須同步使用。它不能在非同步回呼或任何 await 語句之後呼叫。有關更多訊息，請參閱 runInInjectionContext。

回退策略

使用 RenderMode.Prerender 模式時，您可以指定一個回退策略來處理尚未預渲染的路徑的請求。

可用的回退策略有：

  • Server：回退到伺服器端渲染。如果未指定 fallback 屬性，這是預設行為。
  • Client：回退到用戶端渲染。
  • None：無回退。Angular 將不會處理未預渲染的路徑的請求。
// app.routes.server.tsimport { RenderMode, PrerenderFallback, ServerRoute } from '@angular/ssr';export const serverRoutes: ServerRoute[] = [  {    path: 'post/:id',    renderMode: RenderMode.Prerender,    fallback: PrerenderFallback.Client, // Fallback to CSR if not prerendered    async getPrerenderParams() {      // This function returns an array of objects representing prerendered posts at the paths:      // `/post/1`, `/post/2`, and `/post/3`.      // The path `/post/4` will utilize the fallback behavior if it's requested.      return [{ id: 1 }, { id: 2 }, { id: 3 }];    },  },];

編寫伺服器相容的元件

某些常見的瀏覽器 API 和功能可能在服務器上不可用。應用無法使用特定於瀏覽器的全域物件，如 window、document、navigator 或 location，以及 HTMLElement 的某些屬性。

通常，依賴於特定於瀏覽器的符號的程式碼應僅在瀏覽器中執行，而不是在服務器上執行。這可以透過 afterEveryRender 和 afterNextRender 生命週期鉤子來強制執行。這些鉤子僅在瀏覽器中執行，在服務器上會被跳過。

import { Component, ViewChild, afterNextRender } from '@angular/core';@Component({  selector: 'my-cmp',  template: `<span #content>{{ ... }}</span>`,})export class MyComponent {  @ViewChild('content') contentRef: ElementRef;  constructor() {    afterNextRender(() => {      // Safe to check `scrollHeight` because this will only run in the browser, not the server.      console.log('content height: ' + this.contentRef.nativeElement.scrollHeight);    });  }}

透過 DI 訪問請求和回應

@angular/core 套件提供了幾個用於與伺服器端渲染環境互動的令牌。這些令牌使您在 SSR 期間能夠訪問 Angular 應用中的關鍵訊息和物件。

  • REQUEST：提供對當前請求物件的訪問，該物件是 Web API 的 Request 型別。這使您可以訪問標頭、cookie 和其他請求訊息。
  • RESPONSE_INIT：提供對回應初始化選項的訪問，該選項是 Web API 的 ResponseInit 型別。這使您可以動態設定回應的標頭和狀態碼。使用此令牌設定需要在執行時確定的標頭或狀態碼。
  • REQUEST_CONTEXT: 提供對與當前請求相關的附加上下文的訪問。此上下文可以作為 handle 函式的第二個引數傳遞。通常，這用於提供不屬於標準 Web API 的與請求相關的附加訊息。
import { inject, REQUEST } from '@angular/core';@Component({  selector: 'app-my-component',  template: `<h1>My Component</h1>`,})export class MyComponent {  constructor() {    const request = inject(REQUEST);    console.log(request?.url);  }}

重要提示： 在以下場景中，上述令牌將為 null：

  • 在建立過程中。
  • 當應用程式在瀏覽器中渲染時（CSR）。
  • 執行靜態站點生成（SSG）時。
  • 在開發過程中提取路由時（在請求時）。

生成完全靜態的應用程式

預設情況下，Angular 會預渲染您的整個應用程式並生成一個用於處理請求的伺服器檔案。這允許您的應用程式向用戶提供預渲染的內容。但是，如果您希望擁有一個完全靜態的站點而無需伺服器，可以透過在 angular.json 設定檔案中將 outputMode 設定為 static 來選擇退出此行為。

當 outputMode 設定為 static 時，Angular 會在建立時為每個路由生成預渲染的 HTML 檔案，但它不會生成伺服器檔案，也不需要 Node.js 伺服器來提供應用程式。這對於部署到不需要後端伺服器的靜態託管提供商非常有用。

要設定此項，請按以下方式更新您的 angular.json 檔案：

{  "projects": {    "your-app": {      "architect": {        "build": {          "options": {            "outputMode": "static"          }        }      }    }  }}

使用 HttpClient 時快取資料

HttpClient 在服務器上執行時快取了傳出的網路請求。這些訊息被序列化並透過服務器傳送的初始 HTML 部分傳輸到瀏覽器。在瀏覽器中，HttpClient 會檢查快取中是否有數據，如果有，則在初始應用程式渲染期間重用它，而不是發出新的 HTTP 請求。HttpClient 一旦應用程式在瀏覽器中執行變為 穩定 狀態，就會停止使用快取。

預設情況下，HttpClient 會快取所有不包含 Authorization 或 Proxy-Authorization 標頭的 HEAD 和 GET 請求。您可以在提供水合作用時使用 withHttpTransferCacheOptions 來重寫這些設定。

bootstrapApplication(AppComponent, {  providers: [    provideClientHydration(withHttpTransferCacheOptions({      includePostRequests: true    }))  ]});

設定服務器

Node.js

@angular/ssr/node 擴充套件了 @angular/ssr，專門用於 Node.js 環境。它提供了更易於在 Node.js 應用程式中實現伺服器端渲染的 API。有關函式和用法範例的完整清單，請參閱 @angular/ssr/node API 參考。

// server.tsimport { AngularNodeAppEngine, createNodeRequestHandler, writeResponseToNodeResponse } from '@angular/ssr/node';import express from 'express';const app = express();const angularApp = new AngularNodeAppEngine();app.use('*', (req, res, next) => {  angularApp    .handle(req)    .then(response => {      if (response) {        writeResponseToNodeResponse(response, res);      } else {        next(); // Pass control to the next middleware      }    })    .catch(next);});/** * The request handler used by the Angular CLI (dev-server and during build). */export const reqHandler = createNodeRequestHandler(app);

Non-Node.js

@angular/ssr 為在 Node.js 以外的平台上進行 Angular 應用程式的伺服器端渲染提供了必要的 API。它利用 Web API 的標準 Request 和 Response 物件，使您能夠將 Angular SSR 整合到各種伺服器環境中。有關詳細訊息和範例，請參閱 @angular/ssr API 參考。
